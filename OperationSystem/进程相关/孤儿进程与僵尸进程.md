> **孤儿进程：父进程死了，子进程还活着。**  
> **僵尸进程：子进程死了，父进程还没给它“收尸”。**

理解这两句话之后，我们展开。

## 1. 先理解父进程和子进程

在 Linux/Unix 中，一个进程可以通过 `fork()` 创建另一个进程。

例如：

```text
父进程 A
   │
   │ fork()
   ↓
子进程 B
```

A 是 B 的**父进程**，B 是 A 的**子进程**。

它们接下来可以各自运行：

```text
父进程 A ─────────────→

子进程 B ─────────────→
```

问题来了：

> 如果其中一个先死了，会发生什么？

于是就引出了孤儿进程和僵尸进程。

---

# 2. 什么是孤儿进程？

假设：

```text
父进程 A
   │
   └── 子进程 B
```

正常情况下，两者都在运行。

结果父进程 A **先退出了**：

```text
父进程 A ──── X
               \
                子进程 B ─────────→ 还活着
```

此时 B 就变成了：

> **孤儿进程（Orphan Process）**

因为：

```text
爸爸没了
孩子还活着
```

这就是为什么叫“孤儿”。

---

## 3. 孤儿进程会怎么样？

你可能会问：

> 父进程都没了，那这个子进程谁管？

Linux 会给它找一个新的“家长”。

在传统 Unix 描述里，它会被 `init`（PID 1）接管；现代 Linux 中也可能由被设置为 **subreaper** 的进程接管，例如某些服务管理器。

你面试的时候通常说：

> **孤儿进程会被 init/systemd 等系统进程接管。**

就足够了。

例如：

```text
原来：

父进程 A
   │
   └── 子进程 B


A 退出：

A  X

子进程 B
   ↓
成为孤儿进程
   ↓
被系统中的 reaper 接管
```

B **不会因为父进程死了就必须立即退出**。

它仍然可以继续运行。

所以：

> 孤儿进程本身通常不是什么严重问题，操作系统有机制处理它。

---

# 4. 什么是僵尸进程？

僵尸进程正好反过来。

现在：

```text
父进程 A ─────────────→ 还活着

子进程 B ─── X
              ↑
            已经退出
```

子进程 B 已经执行完毕了。

你可能会想：

> 都执行完了，操作系统直接把 B 删除不就好了？

问题就在这里。

操作系统**不能马上把它所有信息都删除**。

因为父进程可能还想知道：

> “我儿子执行成功了吗？”  
> “它的退出状态是多少？”

比如：

```c
exit(0);
```

或者：

```c
exit(1);
```

父进程需要有办法获得这个退出状态。

因此，子进程退出后，内核会释放它绝大多数资源，但保留一小部分进程信息，例如：

```text
PID
退出状态
资源使用统计等
```

等待父进程来读取。

这个已经结束执行、但还保留着进程表项的状态，就是：

> **僵尸进程（Zombie Process）**

---

# 5. 父进程怎么给它“收尸”？

通过：

```c
wait()
```

或者：

```c
waitpid()
```

例如：

```text
父进程
   │
   ├── fork()
   │
   └── 子进程
          │
          │ 执行完毕
          ↓
        exit()
          │
          ↓
       僵尸状态
          │
父进程    │
wait() ───┘
   │
   ↓
获取子进程退出状态
   │
   ↓
内核彻底回收其进程表项
```

所以你可以把 `wait()` 理解成：

> **父进程给已经退出的子进程“收尸”。**

这不是严谨的操作系统术语，但特别好记。

---

# 6. 为什么僵尸进程是个问题？

一个两个僵尸进程通常没什么。

因为它已经退出了，很多资源已经释放。

例如它不再正常执行代码，也不会继续占用原来完整的用户态内存。

但是它仍然占着一些**内核进程管理信息/进程表项**。

如果父进程一直不 `wait()`，同时疯狂创建子进程：

```text
父进程
 │
 ├── 子进程1 → 死亡 → zombie
 ├── 子进程2 → 死亡 → zombie
 ├── 子进程3 → 死亡 → zombie
 ├── 子进程4 → 死亡 → zombie
 ├── ...
 ├── ...
 └── 子进程100000 → zombie
```

大量僵尸进程会耗尽 PID / 进程表等有限系统资源，最终可能导致：

> **系统无法正常创建新的进程。**

所以僵尸进程长期大量存在是需要解决的问题。

---

# 7. 一个非常容易考的情况

假设：

```text
父进程 A
   │
   └── 子进程 B
```

B 先死：

```text
A 还活着

B → 死亡
    ↓
  zombie
```

因为 A 没有 `wait()`。

那么问题来了：

> 如果 A 后来也死了呢？

这时候 B 原来的父进程不存在了。

它会被系统中的 reaper 接管，随后其退出状态会被回收。

因此通常不会变成一个永远没人处理的僵尸。

---

# 8. 孤儿和僵尸放一起比较

这个表建议你直接记住：

| | 孤儿进程 | 僵尸进程 |
|---|---|---|
| 父进程 | 已退出 | 还活着 |
| 子进程 | **还活着** | **已经退出** |
| 为什么产生 | 父进程先退出 | 子进程退出后父进程没 `wait` |
| 子进程还能执行代码吗 | ✅ 能 | ❌ 不能 |
| 是否已结束 | ❌ 没结束 | ✅ 已结束 |
| 谁处理 | 被系统 reaper 接管 | 父进程 `wait/waitpid` 回收 |
| 大量存在是否危险 | 通常问题不大 | ⚠️ 会占用有限的进程管理资源 |

所以最简单的记忆方法就是：

```text
孤儿：

爸爸死了
孩子还活着

父 ❌
子 ✅


僵尸：

孩子死了
爸爸没收尸

父 ✅
子 ❌
```

---

# 9. 为什么一个叫“孤儿”，一个叫“僵尸”？

名字其实取得非常形象。

**孤儿（Orphan）：**

```text
父进程：死了
子进程：活着

→ 没爸爸的孩子
→ 孤儿
```

**僵尸（Zombie）：**

```text
子进程：已经死了
但是进程表里还有它的信息

→ 死了但还留着“痕迹”
→ 僵尸
```

所以你以后基本不会搞混。

---

# 10. 面试标准回答

面试官问：

> 什么是孤儿进程和僵尸进程？

你可以这样回答：

> **孤儿进程**是父进程已经退出、但子进程仍然在运行的情况。孤儿进程之后会被系统中的 reaper（传统上是 init）接管，所以通常不会造成严重的资源问题。
>
> **僵尸进程**是子进程已经退出，但是父进程还没有通过 `wait()` 或 `waitpid()` 获取它的退出状态，因此内核还需要保留它的部分进程信息。少量僵尸进程问题不大，但如果大量积累，会占用 PID 和进程表等有限系统资源。
>
> 两者最核心的区别就是：**孤儿进程是“父死子活”，僵尸进程是“子死父未回收”。**

如果面试官继续追问：

> **“为什么子进程退出后不能直接彻底删除？”**

你就回答：

> 因为父进程可能需要通过 `wait/waitpid` 获取子进程的**退出状态和相关统计信息**，所以内核需要暂时保留这些信息。

这就把整个知识链串起来了：

```text
fork()
  ↓
创建子进程
  ↓
父先死 ─────→ 孤儿进程
  │
  └── 子先死
        ↓
   父没有 wait()
        ↓
      僵尸进程
        ↓
   wait()/waitpid()
        ↓
      完全回收
```

操作系统面试里，沿着这里继续往下，通常就会问到 **`fork()` 到底做了什么、父子进程共享什么，以及写时复制（COW）是什么**。这几个知识点是连在一起的。
