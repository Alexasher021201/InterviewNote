# 项目难点复盘：RAG 连续追问超时与模型选型优化

> 项目：MultiAgent-Search + RAGFlow  
> 记录日期：2026-10-17（北京时间）  
> 场景：本地 Docker RAGFlow 联调、Agent 执行层治理与知识库问答性能优化  
> 用途：面试讲解、问题复盘、后续维护与性能优化参考

## 1. 案例摘要

在为多智能体项目增加检索模式、工具调用预算和 RAG 必经流程后，联调时出现：同一前端会话中连续两次提问“威龙擅长什么枪械”，第一次知识库查询成功，第二次返回 `ReadTimeout`。新建前端会话后，第一次又能成功，最初看起来像会话状态或上下文污染问题。

排查发现：两次 Elasticsearch 查询都很快，传给 RAGFlow 模型的消息内容也完全一致。Agent 每轮实际上创建独立的 RAGFlow 临时会话，没有把第一轮 RAG 聊天历史累积到第二轮。能够确认的直接失败条件，是执行层治理时引入的统一 20 秒 HTTP 读取超时，与非流式 RAG 问答的实际耗时不匹配；不能据此断言第二次一定存在会话复用缺陷。

同时发现另一个正确性问题：本轮 RAG 查询失败后，主 Agent 仍继续生成答案，并利用 checkpoint 中的上一轮依据回答，前端却显示“任务完成”。这使“完成了一次生成”和“本轮成功获得知识库依据”混为一谈。

处理分为两部分：先拆分超时配置、补充阶段耗时与错误信息，并让严格 `RAG_ONLY` 查询失败时明确终止；随后根据任务性质调整模型选型。用户将 RAGFlow 聊天助手的模型由 `gpt-5` 切换为 `gpt-5-mini` 后，反馈当前观察到的知识库回答阶段耗时已降到 10 秒以内。

**本案例体现的工程能力：用证据区分现象与原因、明确工具失败语义、管理分层超时、验证跨轮隔离，并针对实际任务做模型选型。**

## 2. 业务背景与调用链

系统由主 Agent 协调网络搜索、数据库查询、内部知识和三角洲资料等助手。为避免模型无条件联网，项目增加了 `DIRECT`、`RAG_ONLY`、`RAG_FIRST`、`WEB_ONLY` 等执行策略。

本次问题发生在 `RAG_ONLY` 模式，其主要链路是：

```text
前端发送问题
  → 服务端解析本轮检索策略，创建 RunContext
  → get_assistant_list：查询真实 RAGFlow 聊天助手
  → 选择聊天助手“三角洲”，关联知识库“三角洲行动”
  → create_ask_delete：创建本轮临时会话
  → RAGFlow 问答接口：检索、模型生成、引用处理
  → 清理临时会话，返回结构化检索结果
  → 主 Agent 整理答案
  → 前端显示结果与本轮统计
```

这里有几种容易混淆的对象：

| 对象 | 生命周期与用途 |
| --- | --- |
| 前端会话 `thread_id` | 用户连续对话的容器；作为 LangGraph checkpoint 的会话标识 |
| 本轮执行 `run_id` | 每次用户提问独立生成；关联策略、预算、事件和本轮检索事实 |
| RAGFlow 聊天助手 | 持久配置，指定模型、提示词和关联知识库；本例名称为“三角洲” |
| RAGFlow 临时会话 | 每轮检索创建、结束后清理；不等于前端会话，也不等于聊天助手 |

**同一个前端会话连续提问，不代表复用了同一个 RAGFlow 临时会话。**

## 3. 问题现象与原始时间线

### 3.1 同题连续两轮：第一轮成功，第二轮超时

问题均为：`威龙擅长什么枪械`。两轮使用同一个前端会话和 `RAG_ONLY` 模式。

| 时间 | 第一轮发生的事件 |
| --- | --- |
| 17:11:42 | 提交问题；开始 RAG 前置检索 |
| 17:11:42 | 助手发现完成，开始 `create_ask_delete` |
| 17:11:51 | `rag_outcome=success`，随后开始主模型整理 |
| 17:11:53 | 显示任务完成；模型 1 次、知识库 1 次、搜索 0 次 |

| 时间 | 第二轮发生的事件 |
| --- | --- |
| 17:12:05 | 再次提交相同问题；开始 RAG 前置检索 |
| 17:12:05 | 助手发现完成，开始 `create_ask_delete` |
| 17:12:27 | `rag_outcome=error`，checkpoint 中记录 `error_type=ReadTimeout` |
| 17:12:27 | 旧逻辑仍继续调用主模型 |
| 17:12:30 | 模型说明本次检索失败，但沿用上次依据；前端仍显示“任务完成” |

第一轮 RAG 阶段约 9 秒。第二轮从开始查询到报告错误约 22 秒，这个时长还包含管理请求、临时会话处理等开销，不能直接当作单次模型调用耗时。

### 3.2 后续连续观测并未呈现“越问越慢”

之后记录的“生成知识库回答”阶段耗时：

| 样本 | 场景 | 耗时 |
| --- | --- | ---: |
| 1 | 同一会话第 1 次 | 13.99 秒 |
| 2 | 同一会话第 2 次 | 15.41 秒 |
| 3 | 同一会话第 3 次 | 10.00 秒 |
| 4 | 同一会话第 4 次 | 14.62 秒 |
| 5 | 新会话第 1 次 | 17.42 秒 |

- 同一会话四次均值：`54.02 / 4 = 13.505 秒`，约 13.51 秒。
- 五次总体均值：`71.44 / 5 = 14.288 秒`，约 14.29 秒。
- 范围为 10.00～17.42 秒，没有随对话轮次单调增长。
- 新会话第一次反而最慢，不支持“只要新建会话就一定更快”的判断。
- 17.42 秒距离原 20 秒读取上限仅剩 2.58 秒，正常耗时波动就可能碰到上限。

这些样本支持“20 秒等待余量偏小”的判断，但不能单独解释之前那次请求内部究竟为什么变慢。

## 4. 排查过程：先排除错误假设

### 4.1 假设一：第二轮复用了损坏或未清理的 RAG 会话

检查 `tools/ragflow_tools.py` 中的调用过程：每次查询都会通过 `chat.create_session(name=f"run_{ctx.run_id}")` 创建临时会话，并在 `finally` 中按其 ID 清理。

结合每轮新建的 RunContext，当前实现不是通过前端 `thread_id` 反复引用同一个 RAGFlow 临时会话。后续回归也验证了：同一个 checkpoint 会话的两轮请求使用不同临时会话名称，分别执行清理。

结论：现有证据不支持“前端会话相同导致复用错误”的解释；清理失败或其他并发问题仍应通过明确日志判断，不能只凭代码路径就证明所有场景都安全。

### 4.2 假设二：第二轮历史变长，导致模型输入变大

只读检查 RAGFlow 服务日志中的两次 `[HISTORY]`：

- 两次都只有 `system` 和 `user` 两条消息。
- 对两份消息序列进行了实际内容比较，结果完全一致。
- 用户问题相同，引用资料和模型输入没有因前端追问而增加。

结论：这两次请求不能用“第二轮携带了更多 RAG 聊天历史”解释。

### 4.3 假设三：第二轮知识库检索突然变慢

服务端对应日志记录：

```text
17:11:43.458  Elasticsearch _search：status=200，duration=0.030s
17:12:06.380  Elasticsearch _search：status=200，duration=0.030s
```

两轮都在 Elasticsearch 请求之后记录了模型输入 `[HISTORY]`。

结论：这两次的 **Elasticsearch 查询本身** 不是主要耗时点。这里的 30 毫秒不包括整个 RAG 链路，也不能代替问题向量化、模型生成和引用处理的总耗时。

### 4.4 确认直接触发条件：非流式问答遇到偏短的读取超时

执行层治理时，RAG HTTP 适配层统一使用了：

```python
timeout=(5, 20)  # 连接超时、读取超时
```

而问答使用 `session.ask(..., stream=False)`。服务端需要完成检索、调用模型并处理回答后，客户端才能收到完整结果。模型输入已经记录，不代表回答已经生成完成。

当第二次请求未能在读取等待限制内返回时，客户端抛出 `requests.ReadTimeout`，工具将异常转换成 `status="error"`。

必须区分：

| 问题 | 本次证据能否回答 |
| --- | --- |
| 为什么本轮返回 `error`？ | 能：客户端发生 `ReadTimeout`，被结构化为工具失败 |
| 为什么等待上限容易被触发？ | 能：统一 20 秒读取限制与实测 10～17 秒及偶发更长耗时之间余量不足 |
| 为什么那一次比第一次更慢？ | 尚不能完全回答：缺少当次模型请求结束、内部重试和后处理的完整时间线 |
| 是否存在“第二次调用必然失败”的代码规则？ | 未发现；后续多轮观测和回归均不支持该结论 |

**超时是直接失败机制，不等于已经查明所有后端延迟的根因。**

## 5. 第二个难点：检索失败被历史答案掩盖

旧流程是：

```text
本轮 RAG 返回 error
  → 把错误结果继续交给主 Agent
  → 主 Agent 从 checkpoint 找到上一轮相同问题的成功答案
  → 生成一份“沿用历史依据”的回答
  → 前端显示 task_result / 任务完成
```

复用历史信息本身可以是一种产品能力，但不能在没有明确降级约定时，把它当作“本轮严格知识库查询成功”。

本项目中 `RAG_ONLY` 的契约是：本轮先执行知识库查询，失败时明确报告失败，不私自使用网络补充，也不通过旧答案掩盖当前失败。因此修复时关注的不只是异常有没有被捕获，而是 **业务状态是否真实**。

修复后的不变量：

1. `RAG_ONLY + 本轮检索 error` 必须报告失败。
2. 失败后不再调用主模型，避免它用历史答案生成成功结果。
3. 不发出 `task_result`；前端收到 `error`，本轮结束。
4. 本轮统计中主模型调用数为 0，网络搜索数为 0。
5. `no_hit`、`unverified` 和 `error` 继续区分，不能把“请求失败”解释成“没有相关资料”。

`RAG_FIRST` 默认也会在检索错误时停止。只有服务端明确启用故障降级，才允许进入后续处理；`RAG_ONLY` 不因开启这个开关而允许联网。

## 6. 第一阶段解决方案：可靠性与可观测性修复

### 6.1 按请求性质拆分超时

当前 `prompt/prompts.yml` 中的服务端配置：

```yaml
execution_policy:
  timeout_seconds: 180
  rag_connect_timeout_seconds: 5
  rag_request_timeout_seconds: 20
  rag_completion_timeout_seconds: 90
  rag_cleanup_timeout_seconds: 5
  allow_web_on_rag_error: false
  deltaforce_chat_name: "三角洲"
  default_rag_chat_name: "运营sop助手"
```

| 配置 | 用途 | 取舍 |
| --- | --- | --- |
| 连接超时 5 秒 | 建立服务连接 | 服务不可达时尽快暴露 |
| 管理请求读取超时 20 秒 | 助手发现、确认助手、创建会话等 | 避免轻量管理操作长时间挂起 |
| 问答读取超时 90 秒 | 等待非流式回答 | 给生成阶段合理余量，而不是当成期望耗时 |
| 清理读取超时 5 秒 | 删除临时会话 | 避免清理长期拖住结束流程 |
| 总任务超时 180 秒 | 限制整个业务运行 | 防止各阶段等待累加后无限执行 |

每次请求还通过 `RunContext.remaining_seconds()` 获取剩余预算，收紧单次连接和读取等待。

注意：Requests 的读取超时与业务总耗时不是同一个概念；总任务仍由外层 deadline 管理。异步取消也不能强杀工作线程中已经发出的阻塞 HTTP 请求，因此底层请求超时仍然必要。

**延长超时提高容错空间，不会加快模型，也不是性能优化成果。**

### 6.2 增加可关联的阶段日志

RAG HTTP 请求按如下阶段记录：

| `phase` | 含义 |
| --- | --- |
| `discovery` | 查询聊天助手列表 |
| `resolve_assistant` | 根据已验证 ID 确认助手 |
| `create_session` | 创建本轮临时会话 |
| `ask` | 调用问答接口，等待 RAG 回答 |
| `cleanup` | 清理临时会话 |

失败信息保留 `run_id`、`phase`、`error_type`、`elapsed_ms`、`timeout_seconds`，不把可能包含凭证或服务地址的上游异常正文直接返回前端。

示例结构如下，数值仅为格式示意：

```json
{
  "status": "error",
  "error_code": "RAG_TIMEOUT",
  "error_type": "ReadTimeout",
  "phase": "ask",
  "elapsed_ms": 20000,
  "timeout_seconds": 20
}
```

### 6.3 不做无条件自动重试

问答接口会调用模型，并产生临时会话、生成开销等副作用。客户端超时只说明没有及时拿到结果，不代表服务端已经停止生成。

因此没有把“捕获超时后立即反复重试”作为本次解决方案，以免增加重复生成、成本和后端负载。后续如果增加重试，需要同时明确总 deadline、次数、错误类型和请求幂等或结果复用机制。

## 7. 第二阶段解决方案：按任务选择模型

### 7.1 为什么重新审视模型选型

该知识库案例是典型的短事实查询：文档中已经给出角色对应武器，期望答案较短，重点是忠实提取与引用，不需要复杂规划或长篇推理。

实际检查到 RAGFlow 聊天助手原来使用 `gpt-5@OpenAI`。当时重排模型为空，语音和聊天中的网络补充关闭。因此，优先对生成模型做对照，比盲目优化已经很快的 Elasticsearch 查询更有针对性。

这里更换的是 **RAGFlow 聊天助手的回答模型**，不是只修改 MultiAgent-Search 主 Agent 的模型。两个服务拥有独立配置，主 Agent 的参数不会自动传到 RAGFlow。

### 7.2 用户实际执行的优化与结果

用户在 RAGFlow 聊天配置中，将 `gpt-5` 更换为 `gpt-5-mini`，随后反馈知识库生成回答阶段的观察耗时已经降至 10 秒以内。

| 项目 | 更换前 | 更换后 |
| --- | --- | --- |
| RAGFlow 回答模型 | `gpt-5` | `gpt-5-mini` |
| 已有耗时记录 | 5 个样本，均值约 14.29 秒 | 用户反馈当前观察值低于 10 秒 |
| 正式均值、P95 | 样本不足以作为稳定性能指标 | 尚未收集完整样本 |
| 回答质量结论 | 有成功检索并引用来源的案例 | 尚未完成独立问题集的系统对比 |

能够写入面试材料的结论：**针对当前短事实问答，模型替换取得了可观察的响应时间改善。**

不能据此写成“所有任务稳定低于 10 秒”“已验证 P95 达标”或“准确率完全不变”，也不能给出未经测量的精确降幅和成本节省比例。

模型替换后的表现支持“生成相关环节是值得优先优化的方向”，但不等于完全还原了先前那次慢请求内部的排队、重试或后处理原因。

### 7.3 推理开关与模型推理强度不能混为一谈

检查中还发现：RAGFlow 的“推理增强”开关与 GPT 模型的 `reasoning_effort` 不是同一个参数。前者影响 RAGFlow 的检索/推理流程；后者控制模型自身的推理投入。

当前版本的相关适配代码没有透传 `reasoning_effort`。本次没有实施该参数优化，实际改善来自用户更换聊天模型。面试时不应把“尝试建议”说成已经完成的技术成果。

官方参数资料可参考：<https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_new_params_and_tools>。后续调整前仍需核对具体模型与接口的支持范围。

## 8. 为什么没有立即修改 RAGFlow 的三处源码

排查早期曾考虑在接口、RAG 编排、模型适配三处增加内部埋点。进一步检查本地源码和运行中的容器后发现，RAGFlow 已经计算部分分阶段耗时，并附在响应的 `prompt` 字段中：

- Total
- Check LLM / Check Langfuse tracer / Bind models
- Query refinement
- Retrieval
- Generate answer

但当前安装的 Python SDK 在组装回答对象时，仅保留答案、角色和引用等字段，没有保留这一耗时摘要；项目适配层目前也尚未提取它。

因此，对 **成功请求的性能优化**，可以先在 Agent 适配层提取已有耗时摘要，降低改动和部署成本。这个方案已确认可作为后续方向，但本次尚未实现。

已有汇总也有边界：`Generate answer` 包含生成及部分回答处理，并不能直接分离每一次上游 SDK 请求和重试；发生超时时也不一定能获得最终摘要。若继续定位偶发慢请求，仍可能需要更细的内部开始/结束事件。

部署检查还确认：当前 Docker 容器挂载了日志和配置，没有直接挂载 `api`、`rag` 源码。只修改 `D:\ragflow` 下的 Python 文件不会自动改变运行中的服务。真正修改内部实现时，需要确认版本匹配，并通过诊断镜像或小范围文件挂载使修改生效。

**工程取舍：先复用已有观测能力，再决定是否维护 RAGFlow 源码补丁；每个改动都要考虑实际部署是否生效。**

## 9. 回归验证：不仅看页面“能回答”

本次修复完成时，记录的离线验证结果为 **32 项后端测试和 7 项前端测试通过**。这些是当次修复记录，不代表已经完成生产压测。

其中 `tests/test_rag_timeouts.py` 使用：

- 本地模拟 RAG HTTP 服务，第二次问答故意延迟。
- 真实 RAGFlow SDK 和 Requests 传输路径。
- 真实 SQLite checkpoint，同一个前端会话连续两轮。
- Fake 模型，避免测试访问线上模型和消耗线上问答额度。

关键断言：

| 验证点 | 预期 |
| --- | --- |
| 管理请求和问答配置不同超时 | 问答使用独立读取预算，不沿用管理请求短超时 |
| 同一 checkpoint 连续两轮，第二轮稍慢但未超问答预算 | 两轮均成功，临时会话各自独立 |
| 第二轮超过读取预算 | 返回 `RAG_TIMEOUT`，明确关联 `ask` 阶段 |
| 失败之后是否调用主模型 | 调用数为 0，不复用第一次答案生成成功结果 |
| 是否错误发出完成事件 | 不发出 `task_result` |
| 严格知识库模式是否联网补救 | 本项目网络搜索调用数为 0 |
| 错误是否泄漏异常正文中的敏感信息 | 不泄漏 |
| 单次等待是否受总任务预算约束 | 请求预算按本轮剩余时间收紧 |

## 10. 测量口径与后续优化计划

### 10.1 分清“哪里低于 10 秒”

目前用户记录的是“生成知识库回答”阶段，对应客户端等待 RAG 问答接口的时间，包含服务端检索、模型生成和回答处理。

完整用户等待时间还包括：

```text
前端到服务端
+ 助手发现与临时会话管理
+ RAG 问答接口
+ 临时会话清理
+ 主 Agent 整理
+ 结果传输与展示
```

因此，RAG 问答阶段低于 10 秒，不等于整轮用户请求稳定低于 10 秒。流式输出能改善首字等待体验，也不能直接等同于完整回答耗时下降。

### 10.2 后续应补充的性能与质量评估

以下是计划，不是已完成成果：

1. 建立 20～30 个代表性问题，覆盖短事实、无命中、歧义、多文档和较复杂问题，不只重复同一道题。
2. 固定知识库版本、提示词、输出要求、并发和网络条件，对两种模型分组测试。
3. 区分首次请求与重复请求，避免把缓存命中收益误当作普遍性能提升。
4. 同时统计均值、P50/P95、超时率和回答完整时间；失败样本单独记录，不能只统计成功样本。
5. 校验答案是否受知识库支持、引用是否正确、无依据时是否拒答，以及是否保留必要内容。
6. 记录模型、配置版本、token 与费用，再评估速度、质量和成本之间的取舍。
7. 若计划增加结果缓存，应设计知识库版本失效、权限隔离和时间有效性。本次没有新增应用层结果缓存，但不能排除供应商缓存影响重复问题的耗时，因此仍需用不同问题验证模型替换的收益。

RAGFlow 下游聊天应用也可能配置独立的联网能力。本项目拦截自身搜索工具，不自动等于阻止所有下游服务访问网络；严格知识库模式仍需审计并关闭下游相应开关。本次检查时三角洲助手的聊天网络补充开关为关闭。

## 12. 面试讲述版本

### 12.1 一分钟版本

> 我在给多智能体项目增加严格知识库模式时，遇到过同一会话第一次查询成功、第二次超时的问题。最初怀疑会话状态污染，但我对比了 RAGFlow 日志，发现两次模型输入完全一致，Elasticsearch 查询都只有约 30 毫秒，每轮也创建了独立的临时会话，所以没有把现象直接归因为多轮历史问题。
>
> 能确认的失败条件是：管理接口和非流式问答统一使用 20 秒读取超时，生成耗时稍有波动就容易触发。同时我发现检索失败后主 Agent 会沿用上轮答案，前端仍显示完成。我把超时按阶段拆开，并规定严格知识库模式下本轮失败就终止，补充了同一 checkpoint 连续两轮的回归测试。
>
> 之后针对短事实问答调整模型选型，将 RAGFlow 聊天模型从 GPT-5 换成 GPT-5 mini，用户观察到回答阶段耗时降到了 10 秒以内。这里我把延长超时、错误语义修复和真正的性能改善分开验证，不把它们混成一个优化结论。

### 12.2 深入展开版本：按背景、定位、取舍、验证、结果讲

1. **背景与契约**：项目要求 RAG_ONLY 每轮查询知识库且禁止网络补充，主 Agent 还有 checkpoint 历史，因此必须分清本轮证据和历史证据。
2. **定位路径**：从前端现象出发，检查结构化错误、临时会话生命周期、检索耗时和模型输入，逐项验证假设，而不是先改记忆或重写会话管理。
3. **直接失败机制**：客户端 ReadTimeout；20 秒读取限制偏紧。具体某次上游为什么更慢没有完整证据，保持结论边界。
4. **可靠性取舍**：拆分管理、生成、清理超时，保留总 deadline；失败不盲目重试；严格模式明确失败，不让历史答案掩盖当前故障。
5. **性能取舍**：简单事实问答优先测试更匹配的模型；只换 RAGFlow 回答模型，不混淆主 Agent 模型配置。
6. **验证手段**：用本地模拟 HTTP 服务、真实 SDK 和 SQLite checkpoint 复现慢第二轮，验证正常分支与失败分支；线上实际效果另看用户观测。
7. **结果与边界**：执行错误语义更准确，调用可观测；模型替换后当前观察值低于 10 秒。正式 P95、准确率和多并发表现尚待评测。

## 13. 面试常见追问与回答要点

### 为什么你认为不是会话历史越来越长？

因为对两次真实模型输入做了内容比较，结果完全一致，均只有 system 与 user；同时代码每轮创建新 RAG 临时会话。结论仅针对这两次样本，不泛化为系统不存在任何会话问题。

### 为什么不直接把超时调到很大？

调大超时只是给合理波动留余量，不能加快回答。没有总 deadline 会让资源被长期占用，所以要按阶段配置，并保留整轮预算。

### 为什么第二轮失败后不能直接用第一轮答案？

当前模式承诺本轮查询知识库。静默沿用历史结果会掩盖本轮失败，也可能返回过期依据。若产品需要缓存或历史证据降级，应作为明确能力设计，展示来源和时效，不能默认当成本轮检索成功。

### 为什么不用无限重试提高成功率？

超时不等于服务端取消。重复问答可能继续消耗模型资源，放大后端排队，还会产生重复临时会话。重试应受次数、总时长、错误类型和副作用控制。

### 换成 mini 后是不是准确率一定不变？

不能这样保证。当前简单事实查询取得了实际耗时改善；回答质量还要用独立问题集和引用校验验证。复杂问题是否需要更强模型，应基于评测决定。

### 是不是换模型就算生产级工程？

模型替换只是一个优化手段。工程价值在于明确任务契约、用真实证据定位、分层管理预算、正确表达失败、保留观测信息，并通过可重复测试验证行为。

### 你做了分布式追踪或全链路 APM 吗？

没有。本次做的是单机运行上下文和客户端阶段事件，通过 run_id 关联。完整跨服务 trace、供应商请求关联和持久化指标是后续方向，不能把现有日志包装成已完成的分布式追踪。
