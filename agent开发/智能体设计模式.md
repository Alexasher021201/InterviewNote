Agent 开发里的“设计模式”还没有像 GoF 23 种设计模式那样完全统一，但现在工程实践里已经形成了一批非常常见的模式。

结合你前面问的**工作流、低自主性 Agent、高自主性 Agent**，我建议你先掌握下面这张地图：

```text
                    AI Agent 设计模式
                           │
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
    单 Agent 模式        工作流模式          多 Agent 模式
        │                  │                  │
   ├─ ReAct           ├─ Prompt Chain    ├─ Supervisor
   ├─ Reflection      ├─ Routing         ├─ Peer-to-Peer
   ├─ Planning        ├─ Parallel        ├─ Debate
   └─ Tool Use        └─ Evaluator       └─ Hierarchical
```

如果你刚开始学，最值得优先掌握的是：

> **Prompt Chaining、Routing、Parallelization、Reflection、Tool Use、Planning、ReAct、Supervisor Multi-Agent。**

---

# 一、Prompt Chaining：提示链

这是最简单、也非常常用的模式。

核心思想：

> **不要让一个 Prompt 一次完成复杂任务，而是把任务拆成多个步骤，上一步输出作为下一步输入。**

例如：

```text
用户：
帮我写一篇技术博客

        ↓

Agent 1
分析主题
        ↓
生成文章大纲
        ↓
生成初稿
        ↓
检查技术错误
        ↓
润色
        ↓
最终文章
```

代码思想类似：

```java
String outline = llm("生成大纲：" + topic);

String draft = llm("根据大纲写文章：" + outline);

String checked = llm("检查技术错误：" + draft);

String result = llm("润色文章：" + checked);
```

它最大的特点就是：

```text
A → B → C → D
```

流程是**人提前设计好的**。

所以它属于典型的：

> **低自主性 Agent / Workflow**

优点是稳定、容易调试、成本容易控制。

---

# 二、Routing：路由模式

Routing 就是：

> **先判断任务属于哪一类，再交给对应的 Agent / Prompt / Tool。**

例如做一个客服 AI：

```text
                用户问题
                    ↓
                 Router
                    ↓
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      退款问题     技术问题     物流问题
        ↓           ↓           ↓
   Refund Agent  Tech Agent  Logistics Agent
```

比如用户说：

> 我的订单为什么还没到？

Router 判断：

```text
Intent = Logistics
```

于是：

```text
用户
 ↓
Router
 ↓
物流 Agent
 ↓
物流查询 Tool
 ↓
回答
```

而不是让一个巨大的 Agent 什么都干。

这在企业 Agent 中非常常见。

---

# 三、Parallelization：并行模式

如果多个任务之间**不存在依赖关系**，就没必要：

```text
A → B → C → D
```

可以：

```text
          Task
           ↓
     ┌─────┼─────┐
     ↓     ↓     ↓
     A     B     C
     │     │     │
     └─────┼─────┘
           ↓
        汇总结果
```

例如：

> 分析一家新能源汽车公司。

可以同时进行：

```text
             公司
              ↓
      ┌───────┼────────┐
      ↓       ↓        ↓
   财务分析   技术分析   市场分析
      ↓       ↓        ↓
      └───────┼────────┘
              ↓
          综合分析
```

如果每个任务需要 10 秒：

顺序：

```text
10 + 10 + 10 = 30 秒
```

并行理论上可能接近：

```text
max(10,10,10) ≈ 10 秒
```

当然实际还有网络、模型推理和汇总开销。

---

# 四、Tool Use：工具调用模式

这是 Agent 最核心的能力之一。

LLM 本身主要负责：

```text
理解
推理
生成
```

但它通常不能仅靠模型参数知道：

```text
今天实时天气
数据库里的订单
你的最新邮件
公司内部文档
某个 API 的实时数据
```

所以给 Agent Tools：

```text
                 LLM
                  │
        ┌─────────┼──────────┐
        ↓         ↓          ↓
     Search    Database   Calculator
        ↓         ↓          ↓
       Web       SQL        计算
```

例如：

> 新加坡今天多少度？

Agent 判断：

```text
我不知道实时天气
        ↓
需要调用 Weather Tool
        ↓
weather("Singapore")
        ↓
获得结果
        ↓
LLM 组织答案
```

这里有个非常重要的思想：

> **LLM 负责决策，Tool 负责执行。**

可以理解成：

```text
LLM = 大脑
Tool = 手脚
```

---

# 五、ReAct 模式 ⭐

这是学习 Agent 非常重要的模式。

ReAct 来自：

> **Reasoning + Acting**

简单理解就是：

```text
思考
 ↓
行动
 ↓
观察
 ↓
再思考
 ↓
再行动
 ↓
……
```

例如：

> 帮我查一下某公司的 CEO，然后告诉我他的年龄。

Agent：

```text
Reasoning

我首先需要知道 CEO 是谁。

        ↓

Action

Search(company CEO)

        ↓

Observation

CEO = 张三

        ↓

Reasoning

现在需要知道张三出生日期。

        ↓

Action

Search(张三 birthday)

        ↓

Observation

1980 年 5 月……

        ↓

Reasoning

计算年龄。

        ↓

Action

Calculator(...)

        ↓

Final Answer
```

所以 ReAct 的核心循环可以抽象成：

```text
while (!finished) {

    Reason
       ↓
    Action
       ↓
    Observation
       ↓
}
```

你会发现：

**这就是你前面问的高自主性 Agent 开始出现的地方。**

因为程序员没有规定：

```text
先搜索 CEO
再搜索生日
再计算年龄
```

Agent 自己决定下一步。

---

# 六、Planning：规划模式 ⭐

ReAct 通常偏向：

> **走一步，看一步。**

Planning 则强调：

> **先制定计划，再执行。**

例如任务：

> 帮我调查某公司的竞争力。

Agent 先生成：

```text
Goal
│
│ 分析公司竞争力
│
└── Plan
     │
     ├── 1. 公司基本信息
     ├── 2. 财务情况
     ├── 3. 产品
     ├── 4. 竞争对手
     ├── 5. 市场份额
     ├── 6. 技术优势
     └── 7. 风险
```

然后：

```text
Planner
   ↓
生成 Plan
   ↓
Executor
   ↓
执行 Task 1
   ↓
执行 Task 2
   ↓
...
   ↓
检查 Plan
```

如果执行过程中发现：

> 原来的计划不合理。

还可以：

```text
Plan
 ↓
Execute
 ↓
Observation
 ↓
Replan
 ↓
Execute
```

这就是**动态规划任务**。

注意这里说的 Planning 和你算法里的“动态规划 DP”不是一回事。

---

# 七、Reflection：反思模式 ⭐

Reflection 的核心非常简单：

> **让 AI 检查自己刚刚生成的结果。**

普通模式：

```text
Prompt
  ↓
LLM
  ↓
Answer
```

Reflection：

```text
Prompt
  ↓
生成答案
  ↓
Critic
  ↓
检查问题
  ↓
修改
  ↓
再次检查
  ↓
Final Answer
```

比如 AI 写代码：

```text
生成 Java 代码
      ↓
Reviewer Agent

检查：
- 有没有数组越界？
- null 怎么办？
- 时间复杂度？
- 是否满足题意？
      ↓
发现问题
      ↓
Coder 修改
      ↓
最终代码
```

甚至可以让不同角色完成：

```text
Coder Agent
     ↓
Reviewer Agent
     ↓
Coder Agent
     ↓
Reviewer Agent
     ↓
Final
```

这也是现在 Coding Agent 中很重要的一类思想。

---

# 八、Evaluator-Optimizer：评估—优化模式

它和 Reflection 很像，但更加工程化。

Reflection 更像：

> “看看自己哪里有问题。”

Evaluator-Optimizer 则提前定义**评价标准**。

例如写技术文章：

```text
Generator
    ↓
文章
    ↓
Evaluator
    ↓
┌────────────────────┐
│ 正确性：7/10        │
│ 完整性：6/10        │
│ 可读性：9/10        │
│ 引用质量：5/10      │
└────────────────────┘
    ↓
Optimizer
    ↓
修改
    ↓
Evaluator
    ↓
达到标准？
 ┌──┴──┐
 否    是
 ↓      ↓
继续   输出
```

这个模式对于**可量化质量标准**的任务很好用。

---

# 九、Memory：记忆模式

Agent 有时候需要知道过去发生了什么。

例如：

```text
用户：
我以后 Java 代码都使用 Java 17。

        ↓

Memory

        ↓

以后用户问：
帮我写一下这个算法。

        ↓

Agent 知道：
使用 Java 17
```

从 Agent 系统角度，Memory 又可以进一步分：

```text
Memory
│
├── Short-term Memory
│      当前任务/对话状态
│
├── Long-term Memory
│      长期保存的信息
│
└── Episodic Memory
       过去任务/执行经历
```

Memory 本身是一个非常大的 Agent 研究方向。

---

# 十、Multi-Agent：多 Agent

当一个 Agent 什么都做的时候：

```text
Super Agent

写代码
查资料
设计数据库
测试
写文档
分析需求
……
```

Prompt 和工具会越来越复杂。

所以可以拆成：

```text
                Supervisor
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
   Researcher     Coder       Reviewer
        │           │           │
      搜索资料      写代码       Review
```

每个 Agent：

```text
不同 Prompt
+
不同 Tools
+
不同权限
+
不同职责
```

这就是 Multi-Agent。

---

# 十一、Supervisor：主管模式 ⭐

这是 Multi-Agent 中非常经典的结构。

```text
                  Supervisor
                      │
           “这个任务应该谁做？”
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
 Research Agent   Coding Agent   Data Agent
        │             │             │
        └─────────────┼─────────────┘
                      ↓
                  Supervisor
                      ↓
                 Final Answer
```

Supervisor 负责：

```text
任务拆解
任务分配
结果汇总
决定下一步
```

Worker 负责：

```text
完成具体任务
```

这其实很像现实公司：

```text
项目经理
│
├── 后端
├── 前端
├── 测试
└── 运维
```

---

# 十二、Human-in-the-loop：人在回路模式 ⭐

这个在真正的企业 Agent 里**极其重要**。

Agent 可以自主：

```text
查资料
分析
写草稿
生成代码
```

但是到了高风险操作：

```text
付款
删除数据
发送邮件
修改生产数据库
提交代码
```

停下来：

```text
Agent
 ↓
准备执行：
删除 125 条数据
 ↓
⚠️ Human Approval
 ↓
   ┌──────┴──────┐
批准              拒绝
 ↓                 ↓
执行              Cancel
```

这正好对应我们之前讲的：

> **思考可以高度自主，行动可以严格受控。**

---

# 十三、把这些模式按照“自主性”排列

现在你就可以把前面学的知识串起来了：

```text
自主性低
   │
   │  Prompt Chaining
   │
   │  Routing
   │
   │  Parallelization
   │
   │  Tool Calling
   │
   │  Reflection
   │
   │  ReAct
   │
   │  Planning
   │
   │  Supervisor / Multi-Agent
   ↓
自主性高
```

这不是绝对排序，因为一个系统可以组合这些模式，但非常适合你现阶段建立直觉。

---

# 十四、真实 Agent 往往不是只用一种模式

例如做一个：

> **AI 编程 Agent**

可能组合：

```text
                   用户需求
                      ↓
                   Routing
                      ↓
                   Planner
                      ↓
              拆成多个 Coding Task
                      ↓
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       Search       Coding       Docs
          ↓           ↓           ↓
          └───────────┼───────────┘
                      ↓
                  Tool Use
                      ↓
              编译 / 运行测试
                      ↓
                 Reflection
                      ↓
              测试有没有通过？
                 ┌────┴────┐
                NO         YES
                 ↓          ↓
               Replan      Human
                 ↓        Approval
              修改代码       ↓
                 │        提交代码
                 └──→ ...
```

所以所谓“Agent 架构”，很多时候其实就是：

> **把多个 Agent Design Patterns 组合成一个完整 Workflow。**

---

# 十五、你现在学习 Agent，建议按这个顺序

你现在不用急着把所有模式都学得很深。我建议：

```text
第一阶段
Prompt
  ↓
Structured Output
  ↓
Prompt Chaining
  ↓
Routing
  ↓
Parallelization

第二阶段
Tool / Function Calling
  ↓
ReAct
  ↓
Reflection
  ↓
Planning

第三阶段
Memory
  ↓
RAG
  ↓
Human-in-the-loop

第四阶段
Multi-Agent
  ↓
Supervisor
  ↓
复杂 Agent Workflow
```

然后再去学习具体框架，比如 **LangChain / LangGraph、Spring AI、MCP 等**。

你现在尤其要把 **Workflow、Agent、ReAct、Planning** 这四个概念分清楚。因为后面看到很多 Agent 框架，表面上 API 五花八门，底层其实还是类似的结构：

```text
             用户 Goal
                 ↓
              Workflow
                 ↓
        ┌────────┴────────┐
        ↓                 ↓
     固定流程          Agent 决策
                          ↓
                       Planning
                          ↓
                       Tool Use
                          ↓
                     Observation
                          ↓
                       ReAct Loop
                          ↓
                      Reflection
                          ↓
                     Final Result
```

**框架会变，但这些设计模式不会那么快过时。**掌握这些以后，你再看 Agent 框架源码，会明显更容易理解“为什么要有 Node、State、Tool、Router、Planner、Executor 这些东西”。
