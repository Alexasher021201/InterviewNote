**面试时最重要的一句话：Wiki 是知识的组织与协作管理方式；RAG 是利用外部知识辅助大模型生成答案的技术架构。两者属于不同层次，可以组合使用。**

这里把 Wiki 理解为企业内部的协作文档知识库，例如团队维护的技术文档、产品说明和操作手册。如果你指的是某个“AI 自动生成 Wiki”的具体系统，还需要比较它的知识加工方式。

**1．先把概念讲清楚**

**Wiki 解决的是：知识怎么被写下来、组织起来、维护下去。**

典型形式是页面、目录、分类、链接和版本历史。人可以共同编辑，再通过浏览或搜索找到内容。例如，MediaWiki 支持页面修订、版本比较与回滚。[MediaWiki 官方文档](https://www.mediawiki.org/wiki/Manual:Revision)

**RAG（Retrieval-Augmented Generation，检索增强生成）解决的是：模型回答问题时，怎么获得相关的外部证据。**

典型过程是：

```text
用户提问 → 检索外部资料 → 把相关内容放入模型上下文 → 生成答案
```

它让模型在回答时利用外部知识，通常不需要为了每次知识更新重新训练模型。原始 RAG 论文就使用 Wikipedia 的向量索引作为外部知识来源，这也直接说明：**Wiki 可以成为 RAG 的数据源。**[RAG 原始论文](https://arxiv.org/abs/2005.11401)

可以这样记：

> Wiki 管“知识资产”，RAG 管“回答时如何使用知识”。

**2．从多个维度比较**

以下比较的是典型 Wiki 系统和典型 RAG 应用；具体产品可以同时包含两者。

| 维度 | Wiki | RAG |
|---|---|---|
| 本质 | 知识管理与协作系统 | 检索与生成相结合的技术架构 |
| 核心目标 | 沉淀、组织、维护和共享知识 | 为模型回答提供相关证据 |
| 主要操作 | 编写、编辑、浏览、搜索页面 | 检索、筛选、组装上下文、生成 |
| 知识来源 | 通常以维护好的页面为主 | 可接入 Wiki、PDF、数据库、网页等 |
| 知识组织 | 页面、目录、分类、链接 | 文档、片段、元数据和检索索引等 |
| 用户得到什么 | 原文页面或搜索结果 | 针对问题组织的答案，可附引用 |
| 是否必须用 LLM | 不需要 | 生成环节使用生成模型，当前常见为 LLM |
| 是否必须用向量数据库 | 不需要 | 也不需要；可用关键词、向量或混合检索 |
| 跨文档整合 | 通常由读者完成，也可人工编写汇总页 | 模型可按当前问题整合多份证据 |
| 更新方式 | 修改页面，保留版本记录 | 更新数据源，并同步相关索引与缓存 |
| 主要质量问题 | 内容过期、重复、遗漏、组织混乱 | 检索遗漏、上下文缺失、生成错误、引用不准确 |
| 工程成本 | 内容治理、协作流程与平台维护 | 另有解析、检索、推理、评估和监控成本 |

**两个容易被追问的点：**

- **Wiki 也可以有语义搜索、AI 问答。**当它增加“检索资料后由模型回答”的能力时，就引入了 RAG。
- **RAG 不等于向量检索。**向量检索只是检索方法之一。关键词与向量混合检索、重排序都是常见工程选择。[微软 RAG 技术文档](https://learn.microsoft.com/azure/search/retrieval-augmented-generation-overview?tabs=docs)

**3．放到 Agent 架构里，它们分别在哪一层？**

从 Agent 开发的视角，可以分成三个职责：

```text
知识源：Wiki、产品文档、数据库、业务系统
                  ↓
知识访问：搜索、读取页面、RAG 检索服务
                  ↓
Agent：判断需要什么信息 → 调用工具 → 检查结果 → 决定下一步
```

对应关系是：

- **Wiki**：提供可维护的知识内容。
- **RAG**：为模型提供回答所需的证据。
- **Agent**：根据目标与反馈，决定检索、继续调查还是执行动作。

**有 RAG，不代表就是 Agent。**“每次提问都检索一次，再生成答案”的固定流程，可以只是一个 RAG 问答应用。Agent 的关键在于能动态决定工具调用和后续步骤。Anthropic 也区分了预定义流程的 workflow 与由模型动态控制过程的 agent。[Agent 架构说明](https://www.anthropic.com/engineering/building-effective-agents)

例如，用户要求：

> “帮我判断这个客户是否符合退款条件，并处理退款。”

系统可能需要：

1. 从 Wiki 检索退款政策。
2. 调用订单 API，获得购买时间、金额和订单状态。
3. 综合政策与订单事实，判断是否符合条件。
4. 满足业务授权要求后，调用退款接口。
5. 返回处理结果与政策依据。

这里，**Wiki 提供规则，RAG 提供规则证据，业务 API 提供当前事实，Agent 协调判断与执行。**

这比单纯说“Agent 接一个向量库”更能体现你对架构边界的理解。

**4．用一个具体问题看差异**

假设企业 Wiki 有三篇文档：

- 《退款政策》
- 《会员特殊权益》
- 《促销商品例外规则》

用户问：

> “我是会员，昨天买的促销商品，能退吗？”

**通过 Wiki 查阅：**用户找到相关页面，阅读条款，并自行判断哪些规则适用。

**通过 RAG 问答：**系统检索相关条款，模型结合问题生成答案，并引用依据。

但 RAG 仍可能出错：

- 只检索到退款政策，遗漏促销商品例外规则。
- 片段写着“支持退款”，但适用条件被切到了另一个片段。
- 同时取到新旧版本，模型误用旧政策。
- 证据正确，模型却错误解释了“会员权益是否覆盖促销例外”。

因此，**RAG 可以降低模型缺乏外部知识造成的错误，但不能保证答案正确。**

在工程设计上，要分别判断：**有没有拿到足够的证据，以及有没有正确使用证据。**

**5．面试官真正想听的工程落地能力**

如果面试官问：“公司已有 Wiki，怎么做一个 Agent 知识助手？”你可以按下面的顺序回答。这是一套工程设计思路，而不是所有项目都必须采用的固定配置。

**第一，治理知识源。**

先处理过期页面、重复文档和冲突政策，明确负责人、版本、生效时间与适用范围。

知识源存在矛盾时，换更大的模型并不能自动解决问题。

**第二，保留文档结构和元数据。**

切分内容时尽量保留标题层级、表格、条件与例外条款，而不是只按固定字数切割。每个片段应能追溯到：

```text
文档 ID、标题路径、版本、更新时间、适用范围、访问权限、原文链接
```

固定长度切分可以作为起点，但是否合适需要通过真实问题验证。

**第三，按问题特点设计检索。**

可以从关键词与向量混合检索开始，再根据评估决定是否增加重排序、查询改写或多轮检索。

例如：

- 错误码、订单编号、产品型号：需要重视精确匹配。
- 用户口语与文档措辞不同：语义检索可能有帮助。
- 问题涉及条件和例外：需要检查证据是否完整。

**第四，让权限进入检索链路。**

用户无权访问的内容，不应进入模型上下文。需要同步文档权限，并在检索或读取阶段执行授权检查；不能只靠提示词要求模型“不要泄密”。微软的文档级访问控制也是在查询阶段过滤未授权结果。[访问控制文档](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)

**第五，约束回答并管理更新。**

回答应提供可核对的引用；证据不足时说明缺失信息，存在版本冲突时明确指出。页面修改、删除及权限变化，也要同步影响索引与缓存。

**第六，分层评估。**

| 评估层 | 关注什么 |
|---|---|
| 检索层 | 是否找到了需要的证据，例如 Recall@K；排序是否合理 |
| 回答层 | 是否正确、是否受证据支持、引用是否准确 |
| Agent 层 | 工具选择是否正确、任务是否完成、失败后能否恢复 |
| 运行层 | 延迟、成本、更新滞后，以及越权问题 |

这里可以补一句有分量的话：

> “我会用真实问题建立评估集，并覆盖条件、例外、新旧版本、无答案和权限场景，再根据错误分布优化系统。”

**6．几个高频追问，你可以这样回答**

**“有了 Wiki，为什么还需要 RAG？”**

Wiki 提供知识内容；RAG 可以降低用户查阅和跨文档整合的成本。如果用户只是阅读明确的一篇操作手册，直接打开 Wiki 可能更合适。

**“有了 RAG，还需要 Wiki 吗？”**

需要有可治理的知识源。Wiki 能承担知识维护与协作职责，RAG 使用这些知识生成回答，不能自动替代内容负责人和审核流程。

**“Agent 能不能直接搜索 Wiki，不建向量库？”**

能。Agent 可以调用 Wiki 的搜索和页面读取 API，按需获取内容。如果将检索到的内容用于生成答案，也符合广义的检索增强生成思路。是否建立额外索引，要看搜索质量、数据规模、权限、更新频率与延迟要求。[Agent 上下文检索实践](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**“长上下文模型能不能替代 RAG？”**

对于体量小、范围明确的资料，直接放入上下文可以是一种方案。但面对大量、频繁更新或权限各异的知识，仍然需要选择合适的内容，并管理成本与访问权限。

**“Agentic RAG 和普通 RAG 有什么区别？”**

典型普通 RAG 按预设流程检索和回答；Agentic RAG 允许模型根据中间结果决定是否拆分问题、改写查询、读取更多页面或再次检索。它更灵活，也会增加成本、延迟和评估难度，是否采用应由任务需求决定。

**最后，这段可以直接作为面试时的一分钟回答：**

> RAG 和 Wiki 属于不同层次。Wiki 是知识组织和协作管理系统，负责文档沉淀、结构、版本和维护；RAG 是检索增强生成架构，在回答时获取外部证据，并让模型据此生成答案。
>
> 两者可以结合，Wiki 可以作为 RAG 的知识源。RAG 也不等于向量数据库，它可以使用关键词、向量或混合检索。
>
> 在 Agent 系统中，Wiki 提供知识，检索能力提供证据，Agent 决定何时获取信息以及下一步调用什么工具。落地时，我会重点关注知识质量、结构切分、检索完整性、版本更新、权限传递、引用和分层评估。对于退款这类需要执行动作的任务，还必须结合业务 API 获取实时事实，再按业务授权执行操作。
