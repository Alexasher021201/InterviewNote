# 一、什么是 AI Agent？

对应题目：

> 用大白话说清楚什么是 Agent，它和传统对话系统、Siri 类助手的边界在哪？  
> AI Agent 是什么？为什么要用 Agent 而不是直接调大模型？  
> 请用通俗的话说明什么是 Agent。 

### 标准回答

AI Agent 可以理解为：

> **以大模型作为“大脑”，能够围绕一个目标自主进行任务规划、调用工具、获取环境反馈，并根据反馈继续调整行动，直到完成任务的系统。**

普通 LLM 更像：

```text
用户
 ↓
Prompt
 ↓
LLM
 ↓
回答
```

Agent 更像：

```text
              ┌──────────────┐
              │     用户目标   │
              └──────┬───────┘
                     ↓
              ┌──────────────┐
              │     Agent     │
              │   LLM / Brain │
              └──────┬───────┘
                     ↓
             思考 / 规划 / 决策
                     ↓
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      搜索         数据库         API
        ↓            ↓            ↓
        └────────────┼────────────┘
                     ↓
                 环境反馈
                     ↓
              判断是否完成
                ↙       ↘
              否          是
              ↓           ↓
           继续行动       输出结果
```

核心区别就是：

**LLM 主要负责“生成”，Agent 负责“完成任务”。**

Agent 通常至少包含：

- Model：负责理解、推理和决策
- Tools：调用外部能力
- Memory / State：保存任务状态
- Planning：规划任务
- Agent Loop：执行 → 观察 → 再决策
- Guardrails：权限、安全、终止条件

# 二、为什么不直接调用大模型，而要 Agent？

网页将这道题列为字节、快手、腾讯等公司的相关面试题。

### 标准回答

因为单次调用 LLM 本质上是：

> **输入 → 推理 → 输出**

但真实业务经常不是“一次回答”能解决的。

例如：

> 帮我分析线上支付接口为什么超时。

LLM 本身看不到：

```text
服务器日志
数据库
监控指标
Trace
代码仓库
```

Agent 可以：

```text
发现支付接口异常
      ↓
查询监控
      ↓
发现 DB latency 上升
      ↓
查询数据库
      ↓
发现慢 SQL
      ↓
查询相关代码
      ↓
分析原因
      ↓
输出排查报告
```

所以 Agent 的核心价值可以总结成：

> **让大模型从“回答问题”升级为“执行任务”。**

# 三、Agent 和传统 Siri / 对话系统有什么区别？

网页多次出现了这个问题。

### 标准回答

传统助手通常是：

```text
识别意图
 ↓
匹配预定义能力
 ↓
执行固定流程
```

例如：

```text
“明天早上 8 点叫我起床”

↓ Intent Classification

set_alarm(time=08:00)
```

路径基本是开发者提前写好的。

Agent 更强调：

```text
目标
 ↓
模型自主判断下一步
 ↓
选择工具
 ↓
观察结果
 ↓
动态决定下一步
```

所以最核心的区别是：

> **传统助手主要执行预定义流程，而 Agent 可以根据环境反馈动态决定下一步行动。**

# 四、Agent 和 Workflow 有什么区别？

这是非常重要的一题，网页显示字节、百度、腾讯广告、得物等相关面试中出现过。

可以先记一句：

> **Workflow 强调确定性，Agent 强调自主性。**

### Workflow

执行路径提前确定：

```text
A
↓
B
↓
C
↓
D
```

例如退款流程：

```text
查询订单
 ↓
检查退款资格
 ↓
计算金额
 ↓
退款
 ↓
发送通知
```

### Agent

路径不是完全提前确定：

```text
Goal
 ↓
Agent
 ├→ Tool A
 ├→ Tool C
 ├→ Tool B
 └→ Tool D
```

模型根据当前状态决定下一步。

### 面试回答

> 如果业务流程明确、规则稳定、对可靠性要求高，我会优先使用 Workflow。
>
> 如果任务路径无法提前确定，需要模型根据环境反馈动态规划和选择工具，我才会使用 Agent。
>
> 实际生产系统通常不是二选一，而是 **Workflow + Agent 混合架构**，用 Workflow 控制关键业务流程，在不确定的节点引入 Agent。

这一点非常重要：

> **不要为了 Agent 而 Agent。**

# 五、单次 Prompt / Workflow / Agent 怎么选？

网页也专门列了这道架构选型题。

你可以用一个非常简单的判断方法。

### ① 单次 Prompt

适合：

```text
输入明确
+
一次推理能完成
+
不需要外部工具
```

例如：

```text
翻译
总结
分类
文本改写
```

### ② Workflow

适合：

```text
多步骤
+
步骤基本固定
+
要求稳定、可控
```

例如：

```text
文档上传
 ↓
解析
 ↓
Embedding
 ↓
检索
 ↓
LLM
 ↓
输出
```

### ③ Agent

适合：

```text
任务复杂
+
执行路径不确定
+
需要动态决策
+
需要调用工具
```

例如：

```text
代码 Debug Agent
运维 Agent
Research Agent
Coding Agent
```

一句话：

> **能 Prompt 就别 Workflow，能 Workflow 就别 Agent。**

因为自主性越高，通常意味着成本、延迟和不可控性也越高。

# 七、ReAct 是什么？

网页显示携程、腾讯、快手等相关面试中出现过。

ReAct =

> **Reasoning + Acting**

核心思想：

```text
Thought
  ↓
Action
  ↓
Observation
  ↓
Thought
  ↓
Action
  ↓
Observation
  ↓
...
  ↓
Final Answer
```

比如：

```text
用户：
帮我查一下订单为什么没有发货

Thought：
需要先查询订单状态

Action：
getOrder(123)

Observation：
订单已支付，仓库未出库

Thought：
需要查询仓库状态

Action：
getWarehouseStatus(...)

Observation：
商品库存不足

Thought：
原因已经确定

Final：
订单未发货是因为库存不足。
```

### 优点

简单、灵活，而且可以根据工具返回结果动态调整下一步。

### 缺点

复杂任务容易：

```text
走一步看一步
↓
缺乏全局规划
↓
重复调用工具
↓
死循环
↓
Token / latency 增加
```

所以生产环境必须增加：

```text
最大循环次数
超时
重复调用检测
工具权限
异常处理
```

---

# 八、Plan-Execute-Replan 是什么？

它的核心思想和 ReAct 不一样。

先规划：

```text
Goal
 ↓
Planner
 ↓
Plan

1. 查询日志
2. 查询监控
3. 查询数据库
4. 分析代码
5. 输出报告
```

然后：

```text
Executor
 ↓
执行 Step 1
 ↓
执行 Step 2
 ↓
...
```

执行过程中如果发现：

```text
原计划不合理
```

就进入：

```text
Replanner
```

重新调整计划：

```text
Plan
 ↓
Execute
 ↓
Observation
 ↓
Replan
 ↓
Execute
```

因此它更适合：

> **长链路、复杂、多步骤任务。**

---

# 九、ReAct vs Plan-Execute-Replan

这题建议直接背这个逻辑。

| | ReAct | Plan-Execute-Replan |
|---|---|---|
| 核心 | 边想边做 | 先规划再执行 |
| 全局规划 | 弱 | 强 |
| 灵活性 | 高 | 高 |
| 实现复杂度 | 低 | 高 |
| 简单任务 | 非常适合 | 偏重 |
| 长任务 | 容易跑偏 | 更适合 |
| 工具调用 | 动态 | 按计划执行 |

面试可以回答：

> ReAct 更像“走一步看一步”，每获得一次环境反馈就决定下一步；Plan-Execute-Replan 更像“先制定路线，再执行，发现路线不对再重新规划”。
>
> 对短任务、工具数量较少的场景，我倾向 ReAct；对于 Research、Coding、复杂运维等长链路任务，我更倾向 Plan-Execute-Replan。

# 十、为什么 Plan-Execute-Replan 需要监管 Agent？

网页单独列出了这个追问。

因为 Planner 制定计划之后：

```text
Planner
   ↓
Executor
```

Executor 不应该无限执行。

需要一个类似 Supervisor 的角色：

```text
             Planner
                ↓
              Plan
                ↓
            Executor
                ↓
             Result
                ↓
           Supervisor
          ↙     ↓      ↘
       完成    重规划    失败
        ↓       ↓        ↓
      Final  Planner   Retry
```

Supervisor 主要负责：

- 判断任务是否真正完成
- 检查执行结果
- 判断是否需要 Replan
- 防止无限循环
- 控制执行预算
- 处理失败和异常

# 十一、复杂场景如何结合 Plan-Execute 和 ReAct？

网页也专门问了这个架构设计问题。

答案就是：

> **外层 Plan，内层 ReAct。**

例如：

```text
             User Goal
                 ↓
              Planner
                 ↓
      ┌──────────┼──────────┐
      ↓          ↓          ↓
    Step1      Step2      Step3
      ↓          ↓          ↓
    ReAct      ReAct      ReAct
     Loop       Loop       Loop
      ↓          ↓          ↓
      └──────────┼──────────┘
                 ↓
             Supervisor
                 ↓
          Finish / Replan
```

Planner 保证：

> **全局方向正确**

ReAct 保证：

> **局部执行灵活**

这是一个非常好的面试回答。

# 十二、最小可用 Agent 需要什么？

网页的问题是：

> 最小可用 Agent 的核心模块是不是一个 ReAct Loop？除了工具调用还必须实现什么？ 

可以回答：

一个最简单的 Agent 可以抽象成：

```text
         ┌────────────┐
         │    LLM     │
         └─────┬──────┘
               ↓
        Decision / Plan
               ↓
         Tool Calling
               ↓
          Observation
               ↓
             State
               ↓
          Agent Loop
```

工程上至少还需要：

```text
① Prompt / System Instruction
② Model
③ Tool Registry
④ Tool Executor
⑤ State / Memory
⑥ Agent Loop
⑦ Stop Condition
⑧ Error Handling
```

特别是最后两个。

否则：

```text
LLM → Tool → LLM → Tool → LLM → Tool...
```

很容易无限循环。

# 十三、Agent 项目整体架构怎么设计？

这是网页列出的“小红书相关题”。

建议你面试画成：

```text
                    User
                      ↓
                API Gateway
                      ↓
                Agent Runtime
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
     Planner        Memory       Guardrail
        ↓             ↓
      Agent ←────── Context
        ↓
       LLM
        ↓
   Tool Selection
        ↓
   Tool Executor
        ↓
 ┌──────┼─────────┬─────────┐
 ↓      ↓         ↓         ↓
MCP    RAG       DB        API
 ↓      ↓         ↓         ↓
 └──────┴─────────┴─────────┘
              ↓
          Observation
              ↓
           Agent Loop
              ↓
            Result
```

工程上还应该有：

```text
Logging / Trace
Metrics
Timeout
Retry
Permission

```

面试的时候说一句会非常加分：

> **Agent 不能只设计“智能层”，还必须设计 Runtime 和工程兜底层。**

因为生产系统真正困难的通常不是“让模型调用一次工具”，而是保证它**稳定、安全、可观测地完成任务**。

# 十四、Agent 项目和传统后端架构有什么区别？

网页也把这列为了基础架构问题。

传统后端：

```text
Input
 ↓
Controller
 ↓
Service
 ↓
固定业务逻辑
 ↓
DB
 ↓
Output
```

程序员决定：

```text
下一步执行什么
```

Agent：

```text
Input
 ↓
Agent
 ↓
LLM Decision
 ↓
Tool
 ↓
Observation
 ↓
LLM Decision
 ↓
...
```

也就是说：

> **传统软件把控制流写在代码里；Agent 把部分控制流交给模型动态决定。**

因此 Agent 会额外带来：

```text
不确定性
工具调用错误
幻觉
死循环
Token 成本
Latency
权限问题
可观测性问题
```

这也是为什么 Agent 工程需要 Runtime、Guardrails、Evaluation 等体系。

# 十五、什么时候做垂直 Agent，什么时候保持泛化？

网页也列出了这道选型题。

### 垂直 Agent

适合：

```text
业务边界明确
专业知识强
工具固定
准确率要求高
```

例如：

```text
运维 Agent
SQL Agent
客服 Agent
代码 Review Agent
```

优点是：

> 工具少、Prompt 明确、权限容易控制、评测容易建立。

### 通用 Agent

适合：

```text
用户需求开放
任务类型很多
工具很多
需要动态组合能力
```

但代价是：

```text
工具选择更难
上下文更复杂
评测更困难
安全风险更高
```

生产环境通常：

> **优先垂直，再逐步扩能力，而不是一开始就做万能 Agent。**

# 十六、Agent 有什么弊端？企业落地最大瓶颈是什么？

网页把这个问题也放在基础架构章节。

建议不要只回答“幻觉”。

可以从五个方面回答：

```text
Agent 企业落地

① 可靠性
   └─ LLM 输出具有不确定性

② 成本
   └─ 多轮 LLM + Tool Calling

③ 延迟
   └─ Agent Loop 链路很长

④ 安全
   └─ Agent 可以真正执行操作

⑤ 可观测 / 评测
   └─ 很难判断到底哪一步出了问题
```

其中最大的变化在于：

> **Chatbot 回答错了，可能只是答案错；Agent 判断错了，可能真的执行错误操作。**

因此生产 Agent 的重点不仅是“智能”，还包括：

```text
Permission
Sandbox
HITL
Guardrail
Tracing
Evaluation
Rollback
```

# 十七、AI Agent 有哪些常见类型？

网页最后还有“Agent 类型划分”的问题。

没有唯一分类标准，面试时可以从**自主程度 + 架构**两个角度回答。

按自主程度：

```text
低自主性
    ↓
Workflow Agent
    ↓
Tool-Using Agent
    ↓
Planning Agent
    ↓
Autonomous Agent
高自主性
```

按架构：

```text
Agent

├── ReAct Agent
├── Planning Agent
├── Router Agent
├── Reflection Agent
├── Supervisor Agent
└── Multi-Agent System
```

重点不是背名字，而是说明：

> **不同类型本质上是在“规划权、工具选择权、执行权”上给模型不同程度的自主性。**

# 十八、Agent 怎么选择底层模型？

网页列出了阿里、滴滴相关的“主 Agent / 子 Agent 是否应该使用同样大小模型”的问题。

不要回答：

> 越强的模型越好。

正确思路是：

```text
能力
准确率
延迟
成本
上下文长度
Tool Calling 能力
结构化输出能力
```

综合权衡。

多 Agent 系统更不需要全部使用最大模型。

例如：

```text
             Supervisor
             强模型
                ↓
       ┌────────┼────────┐
       ↓        ↓        ↓
   Research   Extract   Format
    中模型     小模型     小模型
```

可以总结：

> **复杂规划用强模型，简单执行用小模型。**

这属于 Model Routing。

这样可以显著降低：

```text
Token Cost
Latency
```
