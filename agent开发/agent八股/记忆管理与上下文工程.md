我重新对照了网页。「**记忆管理与上下文工程**」下面一共列了 **19 道题**，从短期/长期记忆、Memory vs RAG，一直到 Context Compression、长任务目标迷失、上下文污染和记忆评测。网页还特别强调，Agent 应用开发岗这部分属于重点，而且现在面试很喜欢继续追问“怎么量化”。

下面按**适合面试直接背诵**的方式整理。

# Agent 记忆管理与上下文工程

## 一、先建立整体概念

### 1. Memory 和 Context 是什么关系？

**Context：当前这一次 LLM 推理时真正能看到的信息。**

例如：

```text
Context
├── System Prompt
├── 当前用户问题
├── 最近对话
├── RAG 检索结果
├── Memory 召回结果
├── Tool Result
└── Skill Instructions
```

**Memory：存储在 Context 外部、可以在未来被重新召回的信息。**

所以：

```text
Memory
   ↓ 召回相关内容
Context
   ↓
LLM
```

一句话：

> **Memory 负责“存什么、怎么找回来”，Context Engineering 负责“这一轮到底让模型看到什么”。**

---

# 二、短期记忆和长期记忆如何实现？如何区分？

这是最基础的一题。题单显示京东、携程、美团都有相关提问。

### 短期记忆 Short-term Memory

主要保存：

> **当前 Session / 当前任务执行过程中需要的信息。**

例如：

```text
用户刚才说了什么
当前任务做到哪一步
已经调用过哪些 Tool
Tool Result
当前 Plan
```

实现可以是：

```text
Conversation History
Agent State
Redis / Memory Store
Checkpoint
```

生命周期通常较短：

```text
Session 开始
 ↓
不断更新
 ↓
任务结束
 ↓
过期 / 摘要 / 持久化重要内容
```

### 长期记忆 Long-term Memory

保存：

> **跨 Session、未来任务仍然有价值的信息。**

例如：

```text
用户长期偏好
历史任务经验
重要事实
过去成功/失败经验
长期项目状态
```

一般需要：

```text
持久化存储
+
Memory Retrieval
```

可能使用：

```text
关系数据库
Vector DB
Document Store
Graph DB
```

### 面试标准回答

> 短期记忆主要服务当前 Session 和当前任务，一般保存最近对话和 Agent State；长期记忆需要跨 Session 持久化，只保存未来仍有价值的信息，并在需要时通过检索重新加入 Context。两者最大的区别是生命周期、存储方式和召回机制。

---

# 三、Agent 记忆系统整体怎么设计？数据库怎么选？

完整链路建议记：

```text
                    Memory System
                         │
      ┌──────────────────┼──────────────────┐
      ↓                  ↓                  ↓
 Memory Write       Memory Store      Memory Retrieval
      │                  │                  │
  是否值得存？       SQL / Vector DB      Query
  存什么？           KV / Graph DB         ↓
  怎么摘要？              │              Retrieve
      │                  │                  ↓
      └──────────────────┴──────────→ Context
```

数据库**不要直接回答“用向量数据库”**。

要看数据类型。

| 数据 | 适合存储 |
|---|---|
| Session State | Redis / KV |
| 用户、任务等结构化信息 | MySQL / PostgreSQL |
| 语义型长期记忆 | Vector DB |
| 文档/历史记录 | Document DB / Object Storage |
| 复杂实体关系 | Graph DB |

实际生产往往：

> **混合存储，而不是一个数据库解决所有 Memory。**

选型主要看：

```text
数据结构
查询方式
持久化要求
一致性
延迟
规模
成本
```

# 四、长期记忆和 RAG 有什么区别？

这是很容易混的一题。

### RAG

解决：

> **模型不知道外部知识怎么办？**

例如：

```text
公司 Wiki
产品文档
技术文档
规章制度
```

通常：

```text
Question
 ↓
Embedding
 ↓
Vector Search
 ↓
Documents
 ↓
Context
 ↓
LLM
```

### Memory

解决：

> **Agent 如何利用过去交互和任务积累的信息？**

例如：

```text
用户之前做过什么
用户偏好
上一次任务做到哪里
过去的成功经验
```

所以：

```text
RAG
→ 检索“外部知识”

Memory
→ 检索“过去经历/状态”
```

但技术实现可能重叠，例如两者都可以使用：

```text
Embedding + Vector DB
```

### 标准回答

> Memory 和 RAG 的底层检索技术可能相同，但语义不同。RAG 主要给模型补充外部知识，Memory 主要保存 Agent 或用户过去交互产生的状态、经验和长期信息。

# 五、Memory 怎么召回？如何避免记忆污染？

不能简单：

```text
Query
↓
Vector Search
↓
Top-K
```

更完整应该：

```text
Current Query
     ↓
Metadata Filter
     ↓
Semantic Retrieval
     ↓
Recency / Importance
     ↓
Rerank
     ↓
Top-K Memory
     ↓
Context
```

Memory 可以综合评分：

```text
Score =
语义相关性
+ 时间新鲜度
+ 重要程度
+ 用户/任务匹配
```

### 防止 Memory 污染

最重要的是做：

```text
User 隔离
Session 隔离
Task / Project 隔离
Memory Type 隔离
Metadata Filter
相关性阈值
Top-K 控制
```

例如不能因为：

```text
“Java”
```

就把用户半年前所有 Java 对话全塞回来。

标准回答：

> **Memory Retrieval 不能只有向量相似度，还需要结合用户、Session、任务类型、时间、重要性等 Metadata 做过滤，再通过 Rerank 控制真正进入 Context 的 Memory。**

# 六、Agent 上下文管理怎么设计？

这是整个章节最核心的问题之一。

可以记成：

```text
                Context Builder
                      │
     ┌────────────────┼────────────────┐
     ↓                ↓                ↓
 System Prompt     User Query        State
     ↓                ↓                ↓
 Skill           Memory Retrieval    Plan
     ↓
 RAG Retrieval
     ↓
 Tool Results
     ↓
 Compression / Filter
     ↓
 Priority + Token Budget
     ↓
                  Final Context
                       ↓
                      LLM
```

核心不是：

> 把能找到的信息全部塞进去。

而是：

> **在有限 Token Budget 内，让模型看到完成当前决策最需要的信息。**

# 七、检索 Agent 怎么做 Context Management？

Research / Retrieval Agent 特别容易：

```text
搜索一次 → 10 篇文章
搜索两次 → 20 篇
搜索十次 → Context 爆炸
```

所以一般：

```text
Search
 ↓
Raw Results
 ↓
去重
 ↓
相关性过滤
 ↓
提取关键段落
 ↓
Rerank
 ↓
摘要 / 压缩
 ↓
Working Context
```

原始大结果可以：

```text
Object Store / File
```

保存，Context 中只留：

```text
摘要 + 引用 + Handle
```

需要时再取。

# 八、Context Engineering 包括哪些环节？

建议把它背成一个生命周期：

```text
Acquire
获取信息
   ↓
Select
选择信息
   ↓
Organize
组织信息
   ↓
Compress
压缩信息
   ↓
Inject
加入 Context
   ↓
Execute
模型推理
   ↓
Update
更新状态
   ↓
Evict
淘汰无价值内容
```

具体包括：

```text
Prompt
Conversation
RAG
Memory
Tool Results
Skills
State
Compression
Token Budget
Context Ordering
```

### 最重要的一环？

没有绝对唯一答案，但面试可以回答：

> **我认为最核心的是 Context Selection，即决定什么信息真正应该进入当前 Context。因为上下文工程不是单纯解决“放不下”，而是提高有效信息密度。压缩、RAG、Memory 本质上都服务于这个目标。**

这个回答比“最重要的是压缩”更好。

# 九、先压缩还是先向量化？

题单专门问了这个问题。

没有绝对答案，要看压缩对象。

如果原文非常长：

```text
Raw Document
 ↓
Chunk
 ↓
Embedding
 ↓
Retrieval
 ↓
对召回结果压缩
 ↓
Context
```

通常不要在 Embedding 前进行**过度摘要**，否则可能丢掉：

```text
关键词
细节
实体
语义信号
```

导致召回能力下降。

更常见：

> **原始内容合理 Chunk 后向量化 → 检索相关 Chunk → 再对召回结果做 Context Compression。**

一句话：

> **检索阶段尽量保留信息，进入 LLM Context 前再压缩。**

# 十、长对话 + Context Window 受限怎么办？

经典方案：

> **Sliding Window + Summary**

例如：

```text
Message 1
Message 2
Message 3
...
Message 100
```

不能全部保留。

变成：

```text
┌─────────────────────┐
│ Earlier Summary     │
│                     │
│ 用户目标...          │
│ 已确认事实...        │
│ 关键决定...          │
└─────────────────────┘

+
最近 N 轮原始 Conversation
```

也就是：

```text
Context =
System Prompt
+ Long-term Summary
+ Recent Messages
+ Current Query
```

### 为什么最近消息保留原文？

因为最近信息：

```text
与当前问题相关度高
细节重要
摘要可能损失信息
```

所以：

> **远端历史摘要化，近端历史保留原文。**

# 十一、Tool Result 怎么压缩？

比如：

```text
query_logs()
↓
返回 100,000 行日志
```

绝对不能全塞 Context。

可以：

```text
Raw Tool Result
       ↓
Filter
       ↓
结构化提取
       ↓
Summary
       ↓
Context
```

### 原地压缩

主 Agent 自己处理：

```text
Tool Result
↓
Main Agent
```

优点：

```text
链路短
延迟低
```

缺点：

```text
占主模型 Context
增加 Token
```

### 独立模型压缩

```text
Tool Result
↓
Compression Model
↓
Summary
↓
Main Agent
```

优点：

```text
主 Context 更干净
可以使用便宜小模型
```

缺点：

```text
额外模型调用
增加 latency
可能产生摘要失真
```

生产中可以：

> **简单结构化结果规则压缩，大型非结构化结果使用专门压缩模型。**

# 十二、为什么 Context 越长，效果反而可能越差？

这是非常值得理解的一题。

因为：

### ① 信息噪声增加

```text
有效信息
被大量无关信息淹没
```

### ② Attention 被分散

模型需要在更多 Token 中识别重要信息。

### ③ 信息冲突

旧信息：

```text
项目使用 Java 17
```

新信息：

```text
已经升级 Java 21
```

如果同时存在，可能产生冲突。

### ④ Lost in the Middle

模型对 Context 不同位置的信息利用能力可能不同，重要信息埋在长上下文中部时可能更容易被忽视。

所以：

> **Context Window 大 ≠ 应该把 Context 塞满。**

Agent 更关注：

> **有效信息密度。**

---

# 十三、为什么指令的位置会影响模型效果？

LLM 对不同位置的信息利用程度并不完全相同。

因此关键指令通常需要：

```text
System Prompt
↓
明确规则

...

Current Task
↓
必要时再次强化关键约束
```

不要把最重要的：

```text
“禁止修改生产数据库”
```

埋在几十万 Token 的中间。

高风险约束更应该：

```text
Prompt
+
Runtime Permission
```

双重保证，而不是只靠 Context。

---

# 十四、快到 Context Window 阈值怎么办？

不要等到：

```text
99% Context
↓
突然压缩全部历史
```

这样：

```text
延迟突然增加
摘要质量下降
用户等待时间增加
关键状态容易丢失
```

应该设置分阶段阈值，例如概念上：

```text
60%
↓
开始清理低价值 Tool Result

75%
↓
摘要旧 Conversation

85%
↓
卸载大型结果

90%
↓
强制 Compaction
```

核心思想：

> **渐进式 Compaction，而不是一次性大压缩。**

---

# 十五、除了压缩，还有什么方法解决 Context Window？

这题非常重要，因为很多人只会回答 Summary。

可以使用：

```text
① Retrieval
   需要时再取

② External Memory
   信息存 Context 外

③ Tool Result Offloading
   大结果卸载

④ Sliding Window
   只保留最近历史

⑤ Progressive Disclosure
   Skill / Tool 按需加载

⑥ Subagent
   把子任务隔离到独立 Context

⑦ Structured State
   只保留关键状态

⑧ Context Reset
   必要时开启新 Session
```

### 大结果卸载

例如 Tool 返回：

```text
50 MB 日志
```

保存：

```text
Object Storage / File Store
```

Context 只保存：

```text
artifact_id = log_123

summary =
payment-service 出现大量 DB timeout

关键时间：
10:30~10:35
```

需要原始数据时再通过 Tool 读取。

# 十六、长任务如何避免“任务目标迷失”？

Agent Loop 很长时：

```text
Goal
↓
Tool
↓
Tool
↓
RAG
↓
Subagent
↓
Tool
↓
...
```

模型可能逐渐忘记：

> 我最开始到底要干什么？

解决办法是维护独立的：

```text
Task State

{
  original_goal,
  constraints,
  plan,
  completed_steps,
  current_step,
  unresolved_items
}
```

每轮 Context 都重新注入关键部分：

```text
Original Goal
Current Plan
Current Step
Constraints
```

### “无限记忆”为什么不现实？

因为：

> **存储可以接近无限，但 Context 不可能无限。**

所以真正需要的是：

```text
Infinite Storage
+
Selective Retrieval
```

而不是：

```text
Infinite Context
```

这句话非常适合面试。

# 十七、Context Pollution 和 Tool Pollution 怎么区分？

### Context Pollution

问题来自：

> **模型当前看到的信息有问题。**

例如：

```text
错误 Memory
过期信息
无关 RAG
恶意网页内容
冲突历史
```

导致：

```text
Context → LLM 决策跑偏
```

### Tool Pollution

可以理解为：

> **工具体系或工具返回结果持续给 Agent 引入错误、噪声或不适当信息，使后续决策被污染。**

例如：

```text
Tool Description 不清楚
Tool 返回错误结果
错误结果被持续写回 Context
重复工具调用产生大量噪声
```

### 什么时候新开 Session？

如果只是局部：

```text
错误 Tool Result
```

可以：

```text
删除 / 修正 Context
↓
继续当前 Session
```

如果已经：

```text
大量历史被错误信息污染
+
Agent State 已经严重偏离
```

则：

```text
保存可靠 State
↓
重新构建干净 Context
↓
新 Session / Resume
```

# 十八、数月历史的长期 Agent，Memory 怎么持续优化？

不能：

```text
所有历史永久保存
+
每次全部检索
```

需要 Memory Lifecycle：

```text
New Memory
   ↓
Deduplication
   ↓
Importance Scoring
   ↓
Consolidation
   ↓
Decay
   ↓
Archive / Delete
```

### Consolidation

例如：

```text
用户第1次说喜欢 Java
用户第5次说主要写 Java
用户第20次说目前后端使用 Java
```

没必要存 3 条。

可以合并成：

```text
主要技术栈：Java
```

同时长期记忆要处理：

```text
过期
冲突
版本
时间
来源
可信度
```

因此 Memory 不是：

> Write Once。

而应该：

> **持续更新、合并、衰减和淘汰。**

# 十九、Memory 怎么量化评测？

题单特别提醒现在面试官很喜欢问“怎么量化”。

可以从四层评估。

### ① Retrieval Quality

```text
Recall@K
Precision@K
MRR
NDCG
```

回答：

> 该召回的 Memory 有没有召回来？

### ② Memory Accuracy

检查：

```text
记忆是否正确
是否过期
是否冲突
```

### ③ Task Performance

最重要：

```text
有 Memory
vs
无 Memory
```

做 A/B Test。

比较：

```text
Task Success Rate
Answer Accuracy
Tool Success Rate
User Satisfaction
```

### ④ Cost

```text
Memory Token Cost
Retrieval Latency
Storage Cost
```

### 面试标准回答

> 我不会只评测 Memory Retrieval 的 Recall@K，因为最终目标不是“找到了多少记忆”，而是这些记忆有没有提升 Agent 的任务成功率。因此会同时做 Retrieval 指标和 End-to-End Task Success Rate，并通过 Memory On/Off 的 A/B Test 衡量实际增益。

# 二十、哪些信息应该写进 Memory？

这题也很容易被项目追问。

**不是所有 Conversation 和 Tool Result 都应该写 Memory。**

可以按照：

```text
Future Utility
未来是否有用？

Stability
是否长期有效？

Importance
是否重要？

Uniqueness
是不是已经有了？

Confidence
信息可靠吗？
```

判断。

适合长期保存：

```text
稳定偏好
长期项目事实
重要决策
可复用经验
关键失败原因
```

通常不值得长期保存：

```text
一次性寒暄
临时 Tool Result
重复信息
低可信推断
很快过期的数据
```

一句话：

> **Memory Write 的标准不是“这轮出现过什么”，而是“未来任务是否值得再次使用”。**

# 二十一、怎么保证 Compression 不丢关键内容？

不能简单：

```text
历史
↓
LLM
↓
“帮我总结一下”
```

更可靠的是**结构化压缩**。

例如要求输出：

```text
Summary

Original Goal:
...

Confirmed Facts:
...

User Constraints:
...

Completed Steps:
...

Important Tool Results:
...

Current State:
...

Unresolved Problems:
...
```

同时关键内容可以设置：

```text
Pinned Context
```

例如：

```text
用户原始目标
安全规则
关键约束
重要 ID
已经确认的事实
```

这些内容：

> **不参与普通摘要，始终保留原文或结构化状态。**

还可以做：

```text
压缩前后关键信息校验
事实一致性检查
摘要版本保存
必要时回查原始记录
```

# 最后把 19 道题压缩成一张知识图

```text
                    Agent Memory
                         │
             ┌───────────┴───────────┐
             ↓                       ↓
       Short-term                Long-term
       当前任务状态               跨 Session
             │                       │
      Conversation / State       Persistent Store
             │                       │
             └───────────┬───────────┘
                         ↓
                  Memory Retrieval
                         ↓
              Filter + Rerank + Top-K
                         ↓
                    Context Builder
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
      Memory            RAG           Tool Result
        ↓                ↓                ↓
        └────────────────┼────────────────┘
                         ↓
                Context Engineering
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       Select         Compress        Organize
          ↓              ↓              ↓
      Relevant       Summary       Priority
      Context        Offload       Token Budget
          └──────────────┼──────────────┘
                         ↓
                        LLM
```

## 面试最值得背的 8 句话

1. **Context 是模型当前能看到的信息，Memory 是存储在 Context 外、未来可以重新召回的信息。**
2. **短期 Memory 服务当前 Session / Task，长期 Memory 服务跨 Session 的未来任务。**
3. **RAG 主要补充外部知识，Memory 主要保存 Agent 过去交互产生的状态和经验。**
4. **Context Engineering 的核心不是把信息塞满，而是在有限 Token Budget 下最大化有效信息密度。**
5. **Memory Retrieval 不能只靠向量相似度，还应该结合 Metadata、时间、重要性和 Rerank。**
6. **长上下文不一定更好，噪声、冲突和 Lost-in-the-Middle 都可能降低模型稳定性。**
7. **真正需要的是近乎无限的外部存储 + 按需检索，而不是无限 Context。**
8. **Memory 的最终价值应该用 End-to-End Task Success Rate 衡量，而不仅仅是 Recall@K。**
